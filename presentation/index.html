Here is the rule for this session: AI helps with the work; people own the problem, the decisions, and the checks. Treat every generated result as a proposal. AI can propose a change; the team decides whether it stays.

01 AI can speed up tasks. Context gathering, alternatives, starter code, test ideas, and review prompts.

02 People decide. Intent, boundaries, trade-offs, acceptance criteria, and output rules. The agent does not know which interpretation the business wants unless we make that visible, and it cannot decide whether an internal field is safe to expose.

03 Building trust. You do not get to trust an agent by hoping. The agent has to earn it: tests and review show what changed, and automatic quality gates keep AI-generated code within the team's standards. Every time those checks catch something, or confirm something, your trust in the agent becomes grounded in evidence. The next slide shows why this matters so much.

04 Use resources responsibly. Choose the model and context for the task. Keep context small and do not use the most expensive model for every request.

Long-context cost: GPT-5.6 Luna / GPT-6 Luna requests with >272,000 input tokens: 2× input/cache rates, 1.5× output for the whole request. Not a blanket rule for all GPT models; check current platform pricing.

The goal is not the shortest possible prompt. Keep the task, acceptance criteria, relevant code, necessary evidence, and security requirements. These four techniques reduce different kinds of context.

RTK reduces command output. Caveman reduces response length without deleting code or requirements. Ponytail reduces unnecessary code changes by reusing what already exists. DCP compression reduces conversation history by summarizing finished context. Do not compress active work or exact error details that are still needed.

OpenAI model documentation, checked 05 October 2026, confirms the threshold for GPT-5.6 Luna and GPT-6 Luna: more than 272,000 input tokens, not total input plus output. The full request uses twice the input and cache rates and 1.5 times the output rate; it is not only the overflow that costs more. This is provider list pricing, not a verified gateway billing policy. Do not assume the same rule for Sol or every GPT model. Public sources are listed in presentation/README.md.

The shortcutJump straight to the factory→AI slop + token burn→More credits + better model→Still slop

One idea carries this whole workshop: autonomy is earned, not configured. Look at the five rungs. Chat. Then a single agent writing code for you. Then in-the-loop agentic coding, where you steer every step and the agent has skills and guards. Then on-the-loop, where you supervise an agent that runs the loop itself. And at the top, a software factory with hundreds or thousands of agents building for you.

You can build towards that factory. But you cannot start there. To step back from the loop, you first have to trust your agents, and that trust is built by the agents themselves, while you watch them work in the loop. The specs, skills, guards, and retros around them are what make that visible: the guard that catches a mistake, the review that confirms the result, the retro that fixes a repeated slip. Today we walk through exactly these building blocks, as an introduction. This workshop does not move you up a rung. That happens after today, when you build your own workflows into your tools and slowly tweak your skills and agents, so your agents can earn your trust over time.

If you jump straight to the top, you get AI slop and a large token bill. The usual reaction is more credits and a better model. That is rarely the problem. It is a setup problem. A more expensive model on a missing process just produces more expensive slop.

The bar under the ladder is the key: as trust grows, you can climb. Trust is something your agents build with you, not a model you buy. Today you work at rung three. That is where your agents get the chance to earn it.

13 / the software lifecycle

A cycle,
not a prompt.

Hands-on todaySpec, Implement, Verify, Ship (optional)
Shown, not practisedMonitor and Triage
GuardsApplied at every step
ReviewSpec, code and product
RetroImprove the cycle each time

Software development is a cycle, not a prompt. A new idea or a bug report enters at the top. It gets triaged, specified, implemented, verified, shipped and monitored. What we learn from monitoring feeds the next idea or bug.

Review is not one step at the end. It happens at several points: we review the spec before we build, the code before we verify, and the product before we ship.

The outer band is guards: tests, Ruff, pre-commit, CI and the other automatic checks. They apply at every step, not just in a verify step at the end.

In the centre is the retro. After a cycle we look at what happened and improve the environment: a skill, an instruction, a guard. The cycle should be a bit better every time.

AI can help with all of this. Today you practise the highlighted steps: spec, implement and verify, with guards and review across them and a retro to finish. Triage and monitor are dimmed: we show how agents can do them, but there is no hands-on. Ship is optional hands-on if you have the GitHub CLI available.

Both options use the same grilling process. The interview asks the current frontier, offers recommended answers, waits for our answers, and recomputes the next questions.

/grill-me is stateless. The conversation is the only place the decisions live. Use it when you need to settle a decision in the current session and do not need to update project documents.

/grill-with-docs is stateful. It combines grilling with domain-modeling and records settled decisions in project documents such as ADRs and glossary entries. A later session, or another person, starts from those documents instead of from nothing.

After specification, I usually start a new session before implementation. The current session has done its job: it has resolved the questions, written the acceptance criteria, and recorded the boundaries.

I use the /handoff skill to write the context the next session needs. That handoff includes the ticket, the decisions we made, the relevant files, the checks to run, and the next action. It should not copy every conversation detail. It should make the next session startable.

Then I start a fresh session and implement one ticket. If there are several tickets, I normally use one implementation session per ticket. This keeps the context focused and makes it easier to see what belongs to each change.

24 / why spec and guards matter

Spec and guards
keep the agent on the rails.

RAIL ONESpecAcceptance criteria say where the track goes.
RAIL TWOGuardsTests, Ruff, pre-commit, CI keep it there.

If you remember one thing from the hands-on, make it this picture. The agent is a fast train. Speed is not the problem. Direction is.

Two rails keep it on track. The spec is one rail: it fixes where the track goes, with acceptance criteria and out-of-scope notes. The guards are the other rail: tests, Ruff, pre-commit and CI catch mistakes automatically.

Without them the train still moves, probably faster, but it ends up off the tracks. That is AI slop. Spending time on the spec and the guards is what makes the agent trustworthy enough to run unattended later.

The retro is the centre of the lifecycle and the last hands-on step. The point is that the cycle improves every time you go round it.

Run the /retro skill on the session you just finished. It reads the session and looks for improvements to the agent's environment: missing instructions, unclear skills, checks that would have caught a problem earlier. Pick one improvement and write it into a file in the repository.

This is how trust grows. Each retro turns a mistake or a slow step into something the next session does not have to rediscover.

Next slide: why you should not automate this. Do not automate the retro. It is tempting to let an agent run the retro and apply every suggestion by itself. That causes drift: every session adds a rule, and soon you have a huge AGENTS.md and pile of skills that the agent half-ignores, and a setup that may break with the next model. You have to verify the suggestions yourself and choose what changes and what does not. Small and deliberate beats big and automatic.

One point to take home: trust is built, not bought. You can build towards a software factory where agents build for you. But if you start there, before your agents have built trust with you in the loop, you get AI slop and a big token bill. Switching to the most expensive model does not fix that. It is a setup problem.

First, stay in the loop. You decide, the agent proposes. Second, write down what you learn: specs, skills, guards and retros, so the next cycle is better than this one. Third, only then step back. Choose the model and context for the task, keep context small, and remember that a pricier model can't always fix a missing process.
